# ADR-006: Cloudflare Pages with `next-on-pages` Adapter

- **Status:** Accepted
- **Date:** 2026-05-24
- **Deciders:** Engineering lead
- **Phase:** 2 — Analysis & Planning

## Context

Phase 0 NFR-8 constrained hosting to Cloudflare Pages plus Workers, and
ADR-004 picked Cloudflare D1 for persistence. ADR-002 chose Next.js. We
need to confirm the deployment target and the adapter.

## Decision

We will deploy the Next.js application to **Cloudflare Pages** using the
**`@cloudflare/next-on-pages`** adapter. D1, KV (if needed), and secrets
are bound via Pages bindings. The repository's existing `wrangler.jsonc`
will be replaced with the configuration generated by the adapter plus the
D1 binding.

Environments:

- **local** — `wrangler pages dev` with a local D1 SQLite file.
- **preview** — every PR builds a Cloudflare preview deploy.
- **production** — pushes to `main` deploy to the production project.

## Alternatives Considered

| Option | Pros | Cons | Why not chosen |
|---|---|---|---|
| Vercel | First-class Next.js support | Outside chosen platform; would force D1 → Postgres rework | Rejected by Phase 0 constraint |
| AWS (Amplify or ECS) | Familiar to many | Heavier ops; abandons existing CF investment | Rejected |
| Cloudflare Workers Static Assets (without Pages) | Newer Cloudflare path | Less mature for Next.js apps today | Defer; revisit if Pages adapter friction grows |
| Cloudflare Pages + `next-on-pages` | Matches Phase 0; D1 local bindings; preview deploys | Adapter constraints (no Node-only APIs, edge runtime) | **Chosen** |

## Consequences

- **Positive:** keeps the Phase 0 promise.
- **Positive:** preview deploys per PR enable cheap UAT.
- **Negative:** adapter restricts Node APIs; we will pick libraries with
  edge-runtime support up front (Drizzle ✓, Zod ✓, AI SDK ✓).
- **Risk:** Workers CPU time limit (default 30s on paid plan) caps
  long-running LLM calls. Mitigation: streaming and 60s budget set in
  `wrangler.toml`.
